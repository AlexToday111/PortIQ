# Architecture

TradeLab Portfolio starts as one Spring Boot application and one PostgreSQL database: a modular monolith. A single deployable application keeps local development, transactions, migrations, and operations straightforward for a private assistant. There is no current requirement that justifies distributed services, network coordination, or a message broker.

## Current packages

The base package is `ru.ba6kir.tradelab`:

- `TradeLabApplication` is the bootstrap entry point and enables typed configuration scanning.
- `config` contains the validated immutable `DatabaseProperties` and connection-pool wiring. These classes configure infrastructure and contain no investment logic. Credentials come from the environment, are separate from the JDBC URL, and are redacted in the properties' diagnostic representation.
- `common.metadata` contains the read-only `ApplicationMetadata` JPA mapping for the installation record owned by Flyway. There is no metadata API, service, or repository because the foundation needs none.
- `telegram` is an independent feature for private command access and operational status; its adapters do not implement investment logic.
- `market` owns equity metadata, latest exchange trade prices, daily OHLCV history and explicit synchronization, with T-Invest/PostgreSQL adapters and thin Telegram handlers.
- `fundamentals` owns verified instrument→asset mapping, provider financial metrics, quality/freshness views, versioned snapshots and a separate reporting calendar.
- `dividends` owns security-specific dividend observations, conservative identity reconciliation, deterministic amount/yield analytics and a manual calendar.
- `analysis` owns asset-sector classification, canonical financial observations, guarded derived formulas, readiness profiles and descriptive peer comparisons.
- `analysis.scoring` adds a separate deterministic experimental scoring layer with frozen inputs, versioned rules, explicit eligibility and immutable audit snapshots.

The market feature now includes instrument metadata and the initial price-data MVP. Do not pre-create empty packages, interfaces, adapters, or generic exception hierarchies. Add a feature when it has working behavior and clear ownership. Keep `common` small; it must not become a container for unrelated domain logic.

## Telegram feature

The TelegramBots 10.3.0 long-polling starter/client are pinned together and compiled against the existing Java 25 / Spring Boot 3.5.16 application. The SDK starter's automatic initializer is explicitly excluded: `TelegramBotConfiguration` creates feature beans only when `tradelab.telegram.enabled=true`. `TelegramProperties` binds environment-backed values and validates mandatory credentials only when enabled. Constructor validation and a redacted diagnostic representation prevent rejected bot tokens from appearing in binding errors. Disabling the feature creates no Telegram transport, polling session, commands, or polling executor and requires no token/owner ID.

The inbound path is `TelegramUpdateConsumer → TelegramCommandDispatcher → TelegramAccessGuard → registered TelegramCommand`. The guard is inside the dispatcher's public entry point, before parsing and handler lookup. It requires an enabled feature, the numeric owner ID, a non-bot sender, a matching private chat ID/type, and no sender-chat impersonation. Missing identity fields fail closed. Only regular message updates are considered. Unauthorized updates receive no response. The outbound sender additionally restricts recipients to the same owner ID.

Each command bean implements `TelegramCommand`, exposing its name, Russian help description, optional argument support, and a plain-text response. Handlers receive arguments, not raw updates, identities, chat IDs, or transport clients; future registered commands cannot accidentally skip dispatcher authorization. Registration rejects duplicate names. `/help` derives its contents lazily from registered command beans. The dispatcher normalizes whitespace/case, validates syntax and arguments, checks bot-name suffixes against the identity returned by `getMe`, and executes at most one handler per update. It never echoes raw command input or logs arguments.

`/start`, `/help`, and `/ping` provide basic interaction. `/status` delegates to `TelegramStatusService`, which reads Spring application readiness, performs `SELECT 1`, uses an injectable UTC clock, and reports scheduled polling state. It returns only safe availability labels; JDBC exception details and internal addresses stay private. This does not add an investment use case or database schema change.

`TelegramPollingLifecycle` is a `SmartLifecycle` bean. After database/JPA initialization, it validates remote bot identity through the SDK, registers an SDK polling session requesting only message updates, and owns shutdown. One managed scheduled thread processes updates sequentially with no extra update queue. HTTP concurrency is limited, connect/read/call timeouts are finite, and polling failures back off to at most 60 seconds. Shutdown closes sessions, cancels HTTP calls, interrupts/awaits the polling executor, and closes HTTP resources. The SDK's default/static update executors are not used.

SDK logging is suppressed because upstream exceptions can contain token-bearing URLs. The adapter emits sanitized startup, stop, polling-failure, delivery-failure, and known-command execution events, without raw exceptions, message contents, credentials, usernames, or chat IDs. Registration failures discard secret-bearing causes; malformed updates and command failures are contained individually. Messages use plain text and are split without breaking UTF-16 surrogate pairs. Sends are not automatically retried; polling offsets follow SDK semantics rather than durable exactly-once delivery. A process crash may replay an update or lose a response, so future mutating business commands must introduce explicit idempotency before performing side effects.

## Market instrument metadata

The inbound path is the existing authenticated `TelegramCommandDispatcher → MarketCommand → InstrumentService`. `/stock` and `/search` are registered whenever Telegram is enabled, including when the broker integration is disabled, so the owner receives an explicit configuration message. `/help` discovers both handlers through its existing command registry. No market handler receives the transport or raw Telegram identity.

`market.domain.StockInstrument` is an immutable security-level model: stable UID, non-unique ticker/class code, instrument name, optional FIGI/ISIN, currency, exchange, lot, metadata trading status and API availability, retrieval `Instant`, and source. It contains no protobuf types and no company business information. `market.application` owns `StockInstrumentProvider`, `InstrumentStore`, the cache/use cases, and safe typed errors. Application/domain code has no Spring, SDK, JDBC or Telegram dependency. Constructor injection supplies adapters and a UTC clock.

`TInvestStockInstrumentProvider` in `market.infrastructure.tinvest` uses the official Core SDK 1.51 `ConnectorConfiguration`/`ServiceStubFactory` and only the generated Instruments service blocking stub. `FindInstrument` requests `INSTRUMENT_TYPE_SHARE` and defensively excludes other kinds. Search returns short records without pretending to know fields absent from the response. It makes one indexed call, with no full `Shares` scan or result-by-result metadata fan-out. MOEX equity class codes starting `TQ` sort first as a presentation preference; all equity matches remain available. `ShareBy` retrieves complete metadata using `INSTRUMENT_ID_TYPE_UID`, verifies the returned identity, and maps only provider attributes. No SDK object leaves this adapter.

Ticker requests resolve exact matches remotely every time; the local database may contain only a subset, so it cannot establish uniqueness. A unique match proceeds to UID lookup; ambiguous matches are displayed without selecting one. UID lookup prefers unexpired stored metadata, with a configurable default 24-hour lifetime. Explicit refresh bypasses the cache. The response wrapper marks cached versus freshly fetched information; source and retrieval time are persisted independently. Failed refresh never falls back silently to expired data. Local `getCached` remains available for application use when the API is disabled.

`market.infrastructure.persistence.JdbcInstrumentStore` owns `instruments`, introduced by additive migration V2. The provider UID is the primary key. Non-unique ticker/class-code and class-code indexes support catalog queries without assuming global ticker uniqueness. Optional provider attributes are nullable, currency/exchange are explicit, and `updated_at` is `TIMESTAMPTZ`. A single `INSERT … ON CONFLICT (uid) DO UPDATE` provides atomic idempotent writes, and its timestamp condition prevents older responses from overwriting newer data. JDBC is used for this PostgreSQL upsert; the existing foundation JPA mapping is retained. No network request holds a database transaction open.

Integration defaults to disabled and creates no SDK transport in that mode. `InvestProperties` reads environment-backed settings, validates nonblank credentials only when enabled, bounds cache/deadline/retry settings, and redacts its token representation. Deployment must provide a production **read-only** token; the client cannot determine an opaque token's access rights locally. Production TLS endpoint selection is fixed, sandbox is disabled, and there is no fallback. One managed SDK channel is shared and closed on context shutdown. Only Core and its required contract/runtime dependencies are included; no Strategy or trading starter is configured. Instruments and unary price/candle methods are used; there are no streams, account methods or order operations.

Every unary attempt gets a new finite deadline. Timeout/temporary outage retries are bounded to at most three attempts with exponential backoff. Authentication, invalid input, not-found and internal errors are not retried. Rate limiting establishes a cooldown from provider metadata (bounded to 1–3600 seconds, default 60); polling is not blocked sleeping through that cooldown. Errors distinguish disabled configuration, validation, missing instrument, authentication, rate limit, timeout, outage and internal application failure. Logs contain only reason/attempt, never transport exceptions, credentials, query arguments or headers. SDK/gRPC logging is disabled. User replies are plain text with ten-result bounds and bounded provider display fields. Metadata status is explicitly a snapshot, not real-time trading availability.

## Latest prices and daily history (Task 3.2)

The price path is `authenticated TelegramCommandDispatcher → PriceCommand → MarketPriceService → MarketPriceProvider / MarketPriceStore`. Instrument resolution delegates to the existing `InstrumentService`; tickers are never treated as globally unique. `AmbiguousInstrumentException` carries equity choices for UID selection. `/price`, `/history` and `/refresh` are registered through the existing command mechanism and authorization gate. `/stock` optionally reads a stored quote and isolates price failures from metadata. `/status` obtains safe synchronization status through an application service and presentation supplier; operational Telegram tests can still run independently of the market module.

`market.domain.price` contains SDK-independent immutable `MarketQuote`, `DailyCandle` and `HistorySummary`, plus validation. `market.application.price` contains provider/persistence contracts, quote/cache results, synchronization outcomes and the reusable manual synchronization service. `market.infrastructure.tinvest.TInvestMarketPriceProvider` uses `MarketDataService` on the existing authenticated SDK channel. The concrete unary retry/deadline/rate-limit policy was extracted into `TInvestRpc` so instrument and price adapters share the same cooldown without copying the Task 3.1 logic. No new SDK modules were introduced.

The adapter requests `GetLastPrices` for exactly one UID with `LAST_PRICE_EXCHANGE`; an empty list is absence, not zero. Quotation does not carry currency, so the quote model uses the resolved instrument's explicit currency and rejects missing/mismatched metadata. `QuotationDecimals` converts `units + nano / 10^9` using `BigDecimal.valueOf` exclusively, validates nano/sign bounds, and supports negative conversion even though equity price values must be positive. `GetCandles` always requests `CANDLE_INTERVAL_DAY` and exchange source. The pinned SDK's actual response methods (`HistoricCandle.getCandleSource`, `LastPrice.getLastPriceType`) are tested through real generated stubs over an in-memory channel. Missing OHLC, invalid ranges/identity/timestamps, inconsistent high/low, nonpositive stock prices, negative volumes and duplicate timestamps within a response are rejected before a chunk is written. Provider timestamps are retained as UTC instants; `Europe/Moscow` derives the trading date and Telegram display time. A 60-second future clock-skew allowance is explicit.

`V3__create_market_prices.sql` adds:

- `market_quotes`: one row per instrument UID, foreign key to `instruments`; `NUMERIC(29,9)` price, explicit three-letter currency, original quote time, retrieval time and source. Atomic upserts do not let an older trade or older retrieval replace a newer stored quote.
- `daily_candles`: UID foreign key, raw candle time, trading date, four `NUMERIC(29,9)` prices, `BIGINT` volume in provider lots, completeness, source and retrieval time. The primary key `(instrument_uid, candle_time, source)` also serves UID/time scans. A date index supports summaries, and a partial incomplete index supports finalization. Upserts accept fresher data and permit incomplete→complete updates while blocking complete→incomplete regressions.
- `market_sync_state`: per-UID queried coverage, attempt time, durable refresh lease, last successful/failed attempt times and sanitized failure code. The attempt timestamp is recorded for the resulting success/failure. No job table or scheduler is introduced.

`JdbcMarketPriceStore` uses short transactions for candle batches. External calls never hold a production database transaction open. Quote/history phases are independent: a failed API phase leaves previous data intact and can produce partial success. A failed SQL batch rolls back that entire chunk; previously successful chunks remain valid. Coverage is checkpointed only after all history chunks complete successfully, even when a queried interval has no trades. Empty responses never manufacture records or calendar entries. Resolution errors without a UID are returned to the caller and cannot create a per-instrument state row.

Default manual history loading covers 365 calendar dates including today, bounded by configuration to 1–365. Provider requests are split into at most 180-day half-open ranges (at most three initial history requests). Later refreshes backfill an older missing prefix only if requested and fetch an overlapping recent tail from the previous coverage day minus one, or from an earlier incomplete candle. The existing complete middle interval is retained. A failed multi-chunk scan keeps its valid rows but does not advance the coverage checkpoint; a later retry can therefore repeat those chunks safely. Finalized corrections outside the overlap are not automatically rescanned.

Admission is atomic in PostgreSQL: the per-UID cooldown defaults to 60 seconds, rejects an active lease, and survives process restarts. Completion releases the lease; a crashed process's lease expires after one hour. The configured tracked universe is bounded to 20 distinct validated tickers and is loaded from environment configuration, not business constants. `refreshTracked()` resolves each ticker, reports unavailable/ambiguous instruments, and supports an explicit `/refresh tracked` command. No startup synchronization, periodic refresh, notification or investment scheduling exists; production scheduling remains Task 9.

`/price` distinguishes fresh retrieval from cached data, retaining the trade and retrieval timestamps. Fresh retrieval is never labelled a current/executable market quote: the exchange may be closed and the last trade may be old. When the quote API fails after successful UID resolution, an existing stored quote may be returned with a cache/failure label. Ticker resolution itself still requires the provider; there is no unsafe cached-ticker uniqueness shortcut. `/history` uses actual first/last finalized valid observations within the requested trading dates, excludes unfinished candles, shows counts and timestamps, and handles empty/one-observation periods. Price change uses exact subtraction and a guarded decimal percentage calculation, rounded to six decimal places only in the percentage result. It excludes dividends and is not total investment return. Synchronization can fail; data freshness depends on provider and session. No chart, fundamental ratio, portfolio calculation, backtest, recommendation or trading operation was added.

## Fundamental Data Engine (Task 4.1)

`fundamentals` is a dedicated module with domain models/validation, application ports/service, T-Invest/JDBC adapters and Telegram presentation. Its handlers use the existing authorization gate and call application services exclusively. `/fundamentals`, `/reports`, `/fundrefresh` and `/fundstatus` join dynamic `/help`. Existing instrument resolution is exposed through `InstrumentService.resolve`, with the ambiguity exception moved from the price subpackage to shared `market.application` so other features can resolve equities without depending on price use cases.

The identity path is `instrument UID → ShareBy.asset_uid → GetAssetBy` with UID/type/share/reverse-membership checks. Only a verified asset UID reaches `GetAssetFundamentals`. The module keeps instruments, provider assets and company/brand labels distinct; it never merges assets by similar issuer names. Instruments sharing the same verified asset share financial snapshot history. There is no asserted legal-issuer UID where the source supplies only a company/brand label. Reports use instrument UID and remain independent of asset fundamentals.

`TInvestFundamentalsAdapter` reuses an infrastructure-only gateway on the existing Instruments stub, channel and `TInvestRpc` policy. SDK DTOs remain inside adapters. It produces transport-independent source strings and explicit presence information. `FundamentalNormalizer` converts finite doubles through `BigDecimal.valueOf`, preserves provider currency and horizons, records missing/unsupported values, retains questionable observations and diagnostic strings, and computes a deterministic SHA-256 fingerprint. No percentage scaling is guessed: undocumented rate scales receive `SUSPECT`. Implicit-presence protobuf zeros remain uncertain numeric zero. Legitimate negative profit/cash flow is retained; negative multiples receive contextual flags.

The immutable `FundamentalAnalysisView` overlays retrieval, mapping and fiscal-context age warnings on original quality observations. These are separate from provider publication dates, which are unknown in the current fundamentals contract. `usableMetrics()` exposes only unflagged valid observations for future consumers; there is no scoring/recommendation code. Units and exact mapping of 22 source fields plus five unsupported metrics are documented in `FUNDAMENTALS.md`.

Migration V4 adds `asset_identities`, `instrument_asset_links`, `fundamental_snapshots`, `fundamental_metric_values`, `financial_report_events` and `financial_report_sync`. Numeric metrics use `NUMERIC`; optional financial and calendar dates remain nullable and all instants use `TIMESTAMPTZ`. Snapshot foreign keys and per-asset/source version uniqueness preserve identity. A short transaction locks the asset row, checks admission, compares latest content and atomically persists the complete snapshot/metric set. An unchanged response updates last-confirmed time/count only. Corrections and reversions produce new versions, so A→B→A remains traceable. A transaction failure cannot leave partial metrics or destroy an older snapshot; no network request holds that transaction open.

Manual refresh has a durable per-asset cooldown and ten-minute active lease. Default snapshot/mapping/calendar TTL is 24 hours; fiscal-context age has a separate 548-day configurable threshold. Provider failures can return clearly marked stale cache after safe identity resolution. Mapping failures never attach an old snapshot to a newly resolved asset. `/fundstatus` inspects the stored mapping/snapshot state after instrument resolution rather than silently performing a new fundamental fetch.

`GetAssetReports` is a reporting calendar only. The module stores provider publication-calendar date, reporting year/number/type, optional event creation time, retrieval date and a stable event fingerprint. The statement type (e.g. IFRS/RAS) is left unknown. Queries are bounded to at most 180 days in each direction and 500 events; messages show ten. Repeated events are idempotent, revisions remain available diagnostically and the latest successful batch controls the current calendar view. Empty successful responses do not resurrect obsolete events. The calendar cannot supply or reconstruct historical financial statements.

The fundamental-stage scope, source definitions, uncertainty rules, test results and known coverage limits are in `docs/FUNDAMENTALS.md`. Official issuer statement ingestion, legal-issuer consolidation, recommendation/ranking logic, portfolios, forecasts, LLMs and automatic trading remain outside the implemented scope.

## Dividend Intelligence (Task 4.2)

The `dividends` module separates `domain/model`, `domain/service`, `application/port`, `application/service`, `infrastructure/tinvest`, `infrastructure/persistence` and `telegram`. `DividendProvider` and `DividendStore` expose no SDK/JDBC DTOs. `DividendEvent` and observation wrappers preserve provenance, field-quality diagnostics and ambiguity. `DividendAnalytics` computes exact share/lot amounts, dated same-currency event/trailing yields, record-date 365-day sums, annual observed statistics and narrowly comparable annual-event changes. Missing, suspicious, stale or ambiguous inputs cannot produce optimistic yields. Provider amounts retain provider-defined tax semantics.

`DividendService` reuses `InstrumentService.resolve` and the local `MarketPriceService.cachedQuote` application contract. Unlike asset fundamentals, dividends always belong to the exact instrument UID; there is no asset/company join or cross-class transfer. `TInvestDividendAdapter` uses the existing authenticated Instruments stub through its shared deadline/retry/rate-limit gateway, sends instrument UID and converts MoneyValue/Quotation through `QuotationDecimals`. GetDividends filters by UTC record date. Source endpoint inclusivity is unspecified, so bounded requests pad then filter calendar dates locally; absent dates remain diagnostics. Source yield scale and explicit ex-date are unknown and are not reconstructed.

V5 creates `dividend_events` and `dividend_sync_state`, with an instruments FK, exact `NUMERIC` amounts, `DATE` calendar fields, `TIMESTAMPTZ` observation instants, indexed dates/identity anchors, source/content uniqueness and original/normalized source evidence. Original nanoseconds survive in JSON/protobuf diagnostics. Exact repeats only update last-seen metadata. No event ID exists: changed contents sharing creation evidence or indistinguishable calendar evidence remain separate ambiguous versions; sparse cancellations flag possible same-record-date candidates without falsely merging them. Absent observations are preserved. This favors unavailable calculations over unproven additive payments. Details/identity limitations are in [DIVIDENDS.md](DIVIDENDS.md).

Durable per-instrument admission defaults to 60s cooldown and a two-minute active lease. Network calls occur after admission commits and before a separate atomic batch/coverage transaction. Attempt verification rejects superseded late writers. An empty response does not delete history; an API/SQL failure preserves the last valid cache/coverage and records a sanitized reason. The latest successful queried range is stored directly, avoiding invented contiguous coverage. TTL defaults to 24h; requested history is bounded to five years plus the configured forward horizon. No account methods, stream, notification, scheduler or portfolio operation is added.

`ANNOUNCED`, `CANCELLED`, `HISTORICAL_RECORDED` and `UNKNOWN` describe source/date evidence; no status asserts `PAID` or user receipt. Thin `/dividends`, `/divrefresh`, `/divhistory` and `/divcalendar` handlers use the existing owner/private-chat dispatcher and dynamic help. The manual calendar uses the configured tracked universe, retains quality/status labels and bounds chronological output.

## Financial analysis foundation (Task 5.1)

The `analysis` module has domain sector/metric/comparison packages, application services/store port, JDBC/configuration infrastructure and thin Telegram presentation. Domain calculations do not depend on SDKs, Telegram or Spring. Canonical `FinancialObservation` records carry asset/source-snapshot identity, unit/currency, observation type, horizon/period/as-of/retrieval context, inherited quality, provider/derived origin and lineage. Existing V4 provider observations are projected rather than duplicated. Snapshot fiscal dates are not automatically assigned to every individual TTM/MRQ statistic; missing per-metric dates remain explicit and prevent unproven comparisons.

`AssetIdentity` and its existing adapter/store now preserve the raw `GetAssetBy.brand.sector` label. Sector classification belongs to asset UID. Exact recognized source labels take precedence over maintained manual mappings, with explicit verified overrides and compatible manual business-type refinement. A financial label never proves BANK. Missing/unmapped sectors and unsupported non-bank/unknown business types remain explicit. Company-level peer identity requires a separately maintained verified issuer key; brand/name/ticker similarities do not establish that key. Classification freshness is independent of financial snapshot freshness.

`FinancialMetricService` consumes the existing Fundamentals/Dividend application services, preserving safe instrument resolution and security-specific dividend scope. Pure derived calculations enforce identity/snapshot, unit, currency, denominator and verified-period checks; unary earnings yield inherits its source P/E uncertainty. Provider/local ratios remain distinct. Profiles declare required/optional metrics and READY/PARTIAL/INSUFFICIENT_DATA/STALE_DATA/UNSUPPORTED_PROFILE coverage. Multiple required families prevent a single multiple from masquerading as a complete analysis. Configured bank profiles cannot introduce industrial leverage/liquidity rules.

`SectorComparisonService` consumes a bounded configured/persisted classification universe and reads peer snapshots through the new application-facing `FundamentalsService.cachedAsset` contract. It never queries another feature's tables or fetches peer data. Compatible source definitions/origins, exact observation periods, valuation-as-of dates, currencies, sector and business type are required. Each verified issuer counts once; conflicting security representations are excluded. Results preserve candidate identities, observation IDs/timestamps and exclusion reasons. Median is descriptive; metric-specific midrank requires at least five valid other companies and never becomes an overall score. There is no trimming, recommendation or stock-ordering algorithm.

Additive V6 preserves existing data, adds raw sector metadata, creates `issuer_sector_classifications`, `analysis_metric_definitions` and `derived_financial_observations`, and enforces an asset/snapshot composite FK for derived lineage. Financial values use NUMERIC, calendar periods DATE and actual instants TIMESTAMPTZ. Stable derived IDs and local transactional batches provide idempotence/rollback. Classification upserts preserve override precedence and avoid older same-priority regression. External calls occur before persistence transactions. No scheduled work, broker-account operation or scoring table is added.

`/sector`, `/metrics` and `/compare` are ordinary registered commands behind the existing owner/private-chat authorization and dynamic help. Source limits, seed/profile configuration, formulas and verification are documented in [FINANCIAL_ANALYSIS.md](FINANCIAL_ANALYSIS.md). This foundation remains distinct from scoring.

## Fundamental Scoring Engine (Task 5.2)

`analysis.scoring.domain` holds immutable source/result models, profile resolution, configurable bounded piecewise-linear metric rules, a pure four-pillar engine, strict eligibility and evidence-linked risk flags. Application use cases accept instrument/asset UID and expose evaluation, dry-run eligibility and latest/history reads. Domain logic has no provider, persistence, Spring, clock or Telegram dependency; an explicit evaluation instant is supplied. The baseline is .35Q + .25F + .25V + .15D, with all positive-weight pillars mandatory and no missing-value substitution/implicit renormalization.

The production `CachedScoringInputAdapter` captures one read-only REPEATABLE READ snapshot through existing application contracts. Fundamentals, dividend and financial-metric services now expose explicit local-only paths; classification/derived analysis writes are disabled on that path. Capture includes exact values/units/origins/quality, financial and retrieval dates, source snapshot/observation IDs, sector verification, security-specific dividend coverage/history and metadata. No source API runs during capture or scoring. Ticker lookup is an optional separate command-resolution step; UID-based scoring works against stored data with provider access disabled.

BANK uses verified bank-compatible Q/F/V definitions and cannot substitute industrial leverage for missing capital/loan-quality data. OIL_AND_GAS, METALS_AND_MINING and GENERAL_NON_FINANCIAL use explicit researched-in-code assumptions, with separate mining margin/valuation curves. Unknown/non-bank financial profiles remain unscored. Actual unit/date/source/period/identity checks precede every curve. Provider/local variants are selected by an explicit configured origin rather than by whichever score is higher. Negative observations remain legitimate; unavailable evidence stays null. Valuation distress caps and risk flags refer to actual selected financial evidence and are not trading decisions.

V7 adds `scoring_model_versions`, `stock_score_snapshots`, `scoring_metric_contributions` and `scoring_risk_flags`. NUMERIC scores are constrained to [0,100], with an overall value only for SCORED results. A short independent transaction stores the immutable effective model, frozen inputs/result, contribution rows and risk evidence atomically. Configuration fingerprints bind an immutable model/configuration version pair. Duplicate source/configuration/eligibility states reuse the existing snapshot; temporal expiry enters the semantic key so stale data cannot resurrect an earlier scored state. Original evaluation timestamps and version identities remain visible in history.

`/score`, `/scoreinfo` and `/scorehistory` pass the common owner/private-chat guard and join dynamic help. The score is an experimental internal heuristic, not a probability, expected return, intrinsic value or recommendation. The method does not use peer percentiles or global fallback medians; existing descriptive comparisons stay separate. No ranking, stock selections, portfolio logic, backtesting, LLMs or trading were added. Complete assumptions/limitations and files are in [SCORING_METHODOLOGY.md](SCORING_METHODOLOGY.md); Task 5.3 remains unimplemented.

## Dependency boundaries

Organize code by feature (`telegram`, `market`, `fundamentals`, `dividends`, `analysis`, future `portfolio`), rather than putting all controllers, services, and repositories into application-wide layer packages. Within a feature, introduce application/domain/adapter subpackages only when their contents justify them.

Use constructor injection. Domain rules and application use cases must be independent of Telegram SDKs, broker SDKs, HTTP clients, and Spring configuration. Define a provider interface in the feature that consumes the capability once that integration is implemented; place provider-specific code in an adapter implementing it. Do not create empty provider interfaces now.

Features should communicate through small application-facing contracts, not another feature's repositories or persistence entities. Dependencies should point toward domain/use-case code; infrastructure implements those needs. Keep dependencies acyclic. Add events only when a concrete interaction requires them. Cross-feature transactions can remain local database transactions while the application is a monolith.

## Persistence and operations

Flyway is the only schema owner. All changes are versioned SQL migrations under `src/main/resources/db/migration`. Hibernate validates the schema on startup and never mutates it. The V1 installation record proves that migrations ran and is read-only through JPA. Future features own their tables and their persistence mappings.

Use `Instant` and PostgreSQL `TIMESTAMPTZ` for event timestamps. JDBC sessions and Hibernate use UTC. Presentation time zones belong at the user-facing boundary. Future financial values use `BigDecimal`, declared currency/unit semantics, deliberate rounding rules, and `NUMERIC` columns with explicit precision and scale; never binary floating-point money.

Actuator exposes health and info only. Database health participates in overall health and readiness; liveness remains independent of database availability. The JSON console log format is consistent across local and container runs. Do not log tokens, passwords, or sensitive connection material. Spring Boot performs graceful HTTP shutdown; Compose allows it to complete before termination.

## Future features

1. **Telegram commands:** extend the existing authenticated dispatcher with thin handlers calling application use cases. Keep presentation time zones and message formatting outside investment rules; preserve the common authorization gate and add idempotency before introducing mutations.
2. **Market scheduling (Task 9):** build on the explicit synchronization service only when requested. Instrument metadata remains independent from prices. Production scheduling and daily notifications are not implemented in this milestone.
3. **Analytics:** implement deterministic, testable calculations over clearly defined domain inputs. Separate calculations from fetching data and message formatting. Document assumptions and rounding.
4. **Portfolio:** introduce holdings and transaction use cases, precise money types, and persistence in its own feature. Connect to analytics through application contracts rather than repository sharing.

Additional analytics and portfolio use cases remain future directions; financial analysis belongs to `analysis` and dividend-specific deterministic calculations to `dividends`. Revisit process separation only when measured scaling, operational isolation, or ownership requirements justify the added cost. The broker integration supplies metadata, latest exchange trade prices, daily candles, fundamental observations, reporting-calendar and dividend events; there is no investment advice, AI or trading capability.

## Verification

Unit tests cover credential-free JDBC URL construction and redaction. Configuration tests bind the actual YAML/environment placeholders, reject invalid database settings, and check pool settings without opening connections. The integration suite starts the full web application with PostgreSQL 17 via Testcontainers and verifies migrations, JPA schema validation, UTC behavior, migration repeatability, health/readiness, and endpoint exposure. Container tests explicitly skip when Docker is unavailable and must not be described as executed in that case.

Telegram tests use mock transport exclusively. They cover owner-only/private-chat authorization and missing identities, future-handler authorization, all four commands, unknown/malformed input, whitespace/arguments/suffixes, duplicate registrations, disabled startup, enabled validation and registration, long Unicode replies, sanitized transport failures, per-update isolation, and resource cleanup. An enabled full-application test combines mock Telegram transport with a real PostgreSQL Testcontainer. No test proves live Telegram connectivity or needs a real token.

Market tests add mocked-provider service/command coverage, new-command authorization, bounded search/ambiguity, missing optional metadata, source/cache labels, TTL/forced refresh, disabled mode, configuration redaction, and real generated stubs over a scripted in-memory gRPC channel for mapping/deadlines/retries/authentication/rate limits. The client creation test instantiates the actual SDK transport without sending a request. PostgreSQL Testcontainers tests cover repeated upserts and identity semantics.
